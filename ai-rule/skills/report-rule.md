# Report作成ルール

## 1. 目的

Codex CLIおよびClaude Codeで共通利用できる、Report作成の標準ルールを定義する。

Reportは、問題・原因・調査や実装のプロセス・作業内容・根拠・最終結果を記録し、後から人間やAIが経緯を理解し、再利用できるようにする。

## 2. 実行条件

ユーザーが明示的にReportの作成を依頼した場合にのみ、このルールを実行する。

依頼の例：

- Reportを作成して
- 今回の作業をReportにまとめて
- このIssueのReportを作成して
- この調査結果をReportにして

通常の実装・調査・テストが完了しただけでは、自動的にReportを作成しない。

## 3. 保存先

Reportは以下のディレクトリに保存する。

`~/work/report/<repository>/`

`<repository>` は、対象となるGitリポジトリの名前とする。

保存先のディレクトリが存在しない場合は作成する。

対象リポジトリを特定できない場合は、推測で決定せず、ユーザーに確認する。

Reportは対象リポジトリの外部に保存し、対象リポジトリのソースコードや設定ファイルを変更しない。

## 4. ファイル名

Reportのファイル名は、Gitブランチ名に近い命名規則を採用する。

### 4.1 命名形式

Issueに関連する場合：

`issue-<番号>-<短いタイトル>.md`

例：`issue-1234-create-api.md`

PRに関連する場合：

`pr-<番号>-<短いタイトル>.md`

例：`pr-0123-create-api.md`

Issue・PRに関連しない場合：

`report-<YYYYMMDD>-<短いタイトル>.md`

例：`report-20261009-auth-investigation.md`

### 4.2 命名ルール

- `kebab-case` を採用する。英小文字・数字・ハイフンを使用し、単語をハイフンで区切る。
- タイトルは作業内容を簡潔に表す英語とする。
- タイトルの先頭と末尾にハイフンを付けない。
- 連続するハイフンは使用しない。
- スペース、アンダースコア、全角文字は使用しない。
- ファイル名は、内容を識別できる範囲で短くする。
- Issue番号・PR番号は、実際に確認できた番号を使用する。
- 番号が不明な場合は推測で補わない。
- 同名ファイルが存在する場合は、無断で上書きしない。
- 既存ファイルとの関係を確認し、別レポートとして作成するか、既存レポートを更新するかをユーザーに確認する。

### 4.3 タイトルの付け方

タイトルは、作業内容や目的が分かる動詞・名詞を組み合わせる。

例：

- `create-api`
- `fix-auth-error`
- `refactor-database`
- `investigate-timeout`
- `update-aws-config`
- `add-unit-tests`

### 4.4 ブランチ名との整合性

既存のブランチ名が作業内容を適切に表している場合は、その命名を参考にしてよい。ただし、ブランチ名をそのまま使用することは必須としない。

Issue・PR番号を含む場合は、番号を先頭の識別子として配置する。

Reportのファイル名は、ブランチ名と同様に、一覧表示や検索で作業内容を素早く識別できることを優先する。

## 5. Reportのフォーマット

すべてのReportで、以下のフォーマットを基本として使用する。

Reportのタイトルや本文は、対象の作業内容に合わせて具体的に記載する。

---

# <タイトル>

## メタデータ

- **Date:** YYYY-MM-DD
- **Time:** HH:mm:ss ±HH:mm
- **Repository:** <repository>
- **Type:** <issue / pr / report>
- **Reference:**
  - <URL、ファイルパス、フォルダパスなど>

## 1. 問題

発生した問題、解決したい課題、調査の目的を記載する。

問題が発生した背景や、期待される状態と実際の状態の差が分かる場合は、それも記載する。

## 2. 原因

問題が発生した原因を記載する。

- 特定できた原因
- 原因を特定した根拠
- 原因が特定できていない場合は、未特定であること
- 必要に応じて、考えられる仮説と未確認事項

事実と推測を明確に区別する。

## 3. 作業プロセス

問題の調査・分析・設計・実装・検証を、実際に進めた順序で記載する。

各ステップでは、必要に応じて以下を記載する。

- 実施した調査や確認
- 得られた情報
- 検討した選択肢
- 判断した理由
- 次の作業に進んだ理由

実際の作業順序が確認できない場合は、推測で時系列を作らない。

## 4. 作業内容

実際に実施した作業を具体的に記載する。

- 変更したファイルや設定
- 変更したコードや機能
- 実行したコマンドや操作
- 追加・削除・変更した処理
- 実施した設定変更
- 実施したテストや検証

必要に応じて、変更前後の違いや重要なコードを示す。

提案しただけの作業と、実際に実施した作業を区別する。

## 5. 根拠

原因、判断、作業内容、結果を裏付ける情報を記載する。

根拠の例：

- エラーログや実行結果
- ソースコードや設定ファイルの該当箇所
- テスト結果
- コマンドの出力
- 公式ドキュメント
- 関連IssueやPR
- その他、判断の妥当性を確認できる情報

可能な限り、具体的な参照先を記載する。

根拠が確認できない場合は、その旨を明記する。

## 6. 結果

最終的にどのような状態になったかを記載する。

- 実現できたこと
- 問題が解決したかどうか
- 最終的な実装・設定・構成
- 検証方法と検証結果
- 未解決の問題や残課題
- 今後必要となる対応

結果は、以下のいずれかを明確にする。

- **成功:** 期待した状態になり、必要な検証も確認できた。
- **部分解決:** 一部は解決したが、未対応事項が残っている。
- **未解決:** 問題が解決していない。
- **未検証:** 対応は行ったが、結果を十分に確認できていない。

---

## 6. Referenceの記載ルール

ReferenceはURLに限定せず、作業の理解や再検証に役立つ参照先を記録する。

### 6.1 記載できる参照先

1. URL
2. ファイルパス
3. フォルダパス
4. 関連Issue・PR
5. その他、対象を特定できる参照先

### 6.2 記載例

- GitHub Issue: `https://github.com/example/repo/issues/1234`
- ソースコード: `repo_a/internal/api/handler.go`
- 設定ファイル: `repo_a/config/app.yaml`
- フォルダ: `repo_a/internal/api/`
- ログファイル: `/var/log/example/application.log`

可能であれば、ファイルパスに行番号や該当箇所を付ける。

例：

`repo_a/internal/api/handler.go:42-68`

### 6.3 Referenceの注意事項

- 実際に確認できた参照先のみ記載する。
- 存在を確認していないファイルやフォルダのパスを作らない。
- 相対パスを使用する場合は、対象リポジトリのルートを基準とする。
- 絶対パスが必要な場合は、実際のパスを確認して記載する。
- URLとローカルパスを区別できるように記載する。
- 機密情報、認証情報、アクセストークンなどを含めない。
- 参照先が存在しない、またはアクセスできない場合は、その旨を記載する。

## 7. 作成時の共通ルール

- ユーザーの依頼内容と実際の作業内容に基づいて作成する。
- 不明な情報は推測で補完せず、「不明」「未確認」と記載する。
- 事実・推測・提案を明確に区別する。
- 実行していないコマンドやテストを実行済みとして記載しない。
- 成功を確認できていない作業を成功と記載しない。
- 重要な設計判断は、その理由と根拠を記載する。
- 不要な情報や、Reportの目的に関係しない情報は省略する。
- 作業の再現や判断の検証に役立つ具体性を優先する。
- ユーザーが指定した追加要件がある場合は、それを優先する。

## 8. 作成後の確認

Reportを保存した後、以下を確認する。

1. 保存先が正しいこと。
2. ファイル名が命名規則に従っていること。
3. 必須の見出しがすべて存在すること。
4. Referenceに未確認のパスやURLを記載していないこと。
5. 事実と推測が区別されていること。
6. 作業内容と結果に矛盾がないこと。
7. 既存ファイルを無断で上書きしていないこと。

最後に、作成したReportの絶対パスと、内容の概要をユーザーに報告する。
